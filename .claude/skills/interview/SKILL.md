  느낄 때 반드시 사용한다.
  코드베이스를 먼저 분석하고 핵심 질문 최대 3개로 의도를 추출한 뒤 즉시 실행한다.
---

## 목적

작업 시작 전 모호함을 제거한다. 시니어 개발자가 주니어 PR을 리뷰하듯 — 친절하지만 날카롭게, 핵심만 짚는다. 코드에서 이미 파악할 수 있는 것은 묻지 않는다.

---

## 워크플로우

### 1단계: 컨텍스트 수집

아래를 병렬로 실행해 현재 상태를 파악한다.

```bash
git status
git log --oneline -10
```

요청 내용 + 코드베이스 상태를 종합해 다음을 판단한다:
- **작업 유형**: 기능 개발 / 성능 개선 / 테스트 / 리팩토링
- **이미 알 수 있는 것**: 코드에서 파악되면 질문하지 않는다
- **진짜 모호한 것**: 여기에만 질문을 쓴다

### 2단계: 인터뷰

**규칙**
- 한 번에 질문 하나만
- 최대 3개
- 이미 코드/컨텍스트에서 명확한 것은 묻지 않는다
- 질문은 짧고 직접적으로 — 배경 설명 없이 바로 핵심

아래 템플릿에서 가장 모호한 순서로 골라 묻는다.

---

#### 기능 개발 템플릿

| 우선순위 | 질문 |
|---|---|
| WHY (목적) | "이 기능이 없어서 지금 실제로 막히는 게 뭡니까? 구체적으로." |
| WHAT (범위) | "이번에 반드시 들어가야 할 것과 절대 안 들어가야 할 것을 각각 나열하세요." |
| DONE (완료 기준) | "완료 기준이 뭡니까? 어떻게 확인할 건가요?" |

---

#### 성능 개선 템플릿

| 우선순위 | 질문 |
|---|---|
| WHERE (병목) | "병목이 어디입니까? 측정 결과가 있으면 수치로." |
| TARGET (목표) | "현재 수치와 목표 수치. 숫자로 말해주세요." |
| SCOPE (범위) | "어디까지 건드릴 수 있습니까? DB 스키마, 외부 API, 인프라 포함 여부." |

---

#### 테스트 템플릿

| 우선순위 | 질문 |
|---|---|
| LAYER (레이어) | "단위/통합/E2E 중 어느 레이어입니까? 기존 테스트와 어떻게 구분합니까?" |
| CRITICAL (핵심 시나리오) | "가장 깨지면 안 되는 시나리오가 뭡니까?" |
| COVERAGE (기준) | "커버리지 수치 목표가 있습니까, 아니면 케이스 기반입니까?" |

---

#### 리팩토링 템플릿

| 우선순위 | 질문 |
|---|---|
| PAIN (실제 고통) | "이 코드의 어떤 점이 지금 개발 속도를 실제로 늦추고 있습니까?" |
| BOUNDARY (불변 범위) | "동작이 절대 바뀌면 안 되는 범위가 어디입니까?" |
| TRIGGER (지금인 이유) | "왜 지금입니까? 기능 추가나 버그 수정이 트리거입니까?" |

---

### 3단계: 요약 + 즉시 실행

인터뷰가 끝나면 아래 형식으로 요약하고 바로 작업을 시작한다.

```
## 인터뷰 완료

**작업 유형**: [기능 개발 | 성능 개선 | 테스트 | 리팩토링]
**핵심 의도**: [한 문장]
**작업 범위**:
- 포함: ...
- 제외: ...
**완료 기준**: ...

→ 작업 시작합니다.
```

요약 후 사용자 확인 없이 바로 실행한다.

---

## 질문 스타일 가이드

- **나쁜 예**: "혹시 이 기능의 목적이나 배경을 좀 더 설명해 주실 수 있을까요?"
- **좋은 예**: "이게 없어서 지금 실제로 막히는 게 뭡니까?"

- **나쁜 예**: "성능 목표치가 어느 정도 되시나요?"
- **좋은 예**: "현재 p95 레이턴시가 얼마고, 목표가 얼마입니까?"

날카롭되 공격적이지 않게. 모호함을 용납하지 않되 상대를 몰아붙이지 않는다.
